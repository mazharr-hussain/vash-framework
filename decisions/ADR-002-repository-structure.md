# ADR-002: Freeze the VASH repository structure

- **ID:** ADR-002
- **Title:** Freeze the VASH repository structure
- **Activity:** 5.1 (docs/design/5-1_repo_structure.md), brought forward by owner decision
- **Builds on:** ADR-001 (VASH as the application framework, ACCEPTED)
- **Decided by:** Human owner

## Status
ACCEPTED (owner, 2026-11-08)

## Date
2026-11-06 (proposed); 2026-11-08 (D10 added, structure record corrected, accepted)

## Context
VASH is a public tool that anyone can use for any project. Its repository held design documents in
knowledge/, vash_framework/ and runtime/, with no place for the method, catalog, engine and project
scaffold as separate products. The owner and Claude designed the structure over a working session
(5-6 Nov 2026), checked it against three feedback sets, and the owner froze it (v7) with decisions D1-D9.
Before acceptance (8 Nov 2026) the structure was checked against what Wave 1 built, and the owner added
D10: VASH is the development runtime for every project, used from any coding tool.

## Decision
| # | Decision |
|---|---|
| D1 | VASH's own review trail stays in this repository, committed under audit/; runtime/ is git-ignored scratch and is never committed. |
| D2 | The project skeleton is scaffold/project/ (renamed from templates/project/); method/templates/ holds forms only and method/schemas/ the schemas. |
| D3 | Package and command name vash (free on PyPI, checked 5 Nov 2026); semver from 3.0.0 shared by package, release tag and method; repository name vash-framework (owner decision 8 Nov 2026; was vash3-framework). |
| D4 | The design-only stack pack is in wave 1 so VASH works for anyone with no technology chosen. VASH names no application. |
| D5 | Technology independence and $0 outrank every other rule: every technology layer (stack, LLM, git host, CI/CD, cloud) is a catalog category with one adapter per option, chosen per project in project-stack.json; the core names no vendor. R9 becomes "the project's own git host, through the forge adapter". |
| D6 | Pilots are the owner's private Oracle APEX projects, so the oracle-apex pack and the GitHub, GitHub Actions, OCI and LLM adapters are in wave 1; each pilot adopts VASH through its own ADR in its own repository. |
| D7 | src/vash/core/exceptions.py with named errors; data/ (incl. data/intake/) ignored in VASH, the folder exists only in projects; catalog/ci/local-hooks and its adapter in wave 1. |
| D8 | The structure is frozen. One LLM interface independent of any tool; bin/ wrappers only call python -m vash.cli. |
| D9 | src/vash/mcp/ write guard in wave 1 (R6 holds for the pilots); src/vash/core/interfaces.py adapter contract in wave 1; CLI stubs for later-wave commands through NotAvailableYet, reporting the routes actually configured. |
| D10 | VASH is the development runtime for every project, used from any coding tool (harness): Claude Code, VS Code, Google Antigravity, an open-source harness or others. The harness is each developer's own choice, not part of the freeze, so developers of one project may use different harnesses. One instruction file for every harness, AGENTS.md at the repository root, is committed: generated by vash load from method/laws.md and project-stack.json, never hand-edited, and checked for drift like every generated file. Each harness has one loader adapter in catalog/harness/ that writes only that harness's own files (Claude Code: CLAUDE.md and .claude/; VS Code: .github/copilot-instructions.md; others their rule files), pointing to AGENTS.md; these files are git-ignored. Every harness calls the same vash command, so Gate 1, AvA, the write guard and the freeze apply the same way. Wave 1: Claude Code (owner exception OD-1). Wave 2: AGENTS.md generation, the harness adapters and a free open-source harness on the OCI host with the free LLM routes (ADR-001 D6, D7). |

Activity 5.1 completes the frozen structure with what its description requires and the freeze did not
change: naming conventions, file formats (with .gitattributes for LF / UTF-8), branch strategy, the
project repository contents, and the LAW 3 search for the loader / provisioner (Copier proposed).

## Consequences
- The files were moved into this layout in Wave 1 (Step 7), keeping history; the AvA scripts' paths were
  updated in bootstrap stage A.
- Folders are created only when their wave starts; the structure lists them all.
- Structure record corrected to what Wave 1 built: plan/operations/ removed (owner, not needed for waves
  1-3); .github/workflows/project-sync.yml, requirements.lock and docs/reference/versioning.md moved to
  wave 2.
- D10: until the wave 2 harness adapters exist, VASH's own sessions use Claude Code; .claude/ holds only
  the tracked settings.json that starts vash load, and the root CLAUDE.md stays committed. When AGENTS.md
  generation lands, CLAUDE.md and .claude/ become generated and git-ignored.
- Rule R12 is amended (one configured fallback route to local Ollama) and R9 is amended (project state
  on its own git host), in force with this ADR.
- Any change to the structure needs a new owner decision that supersedes this ADR.

## Alternatives Considered
- Keep the review trail in runtime/ (rejected: runtime/ is scratch and never committed; D1).
- Keep templates/project/ next to method/templates/ (rejected: two "templates" folders; D2).
- Stack pack only for the pilot technology in wave 1 (rejected: VASH must work for anyone with no
  technology chosen; design-only pack, D4).
- Hard-code GitHub, GitHub Actions and OCI in the core (rejected: technology independence; D5).
- Tie VASH to one coding tool through committed tool-specific files (rejected: developers choose their
  own harness; one committed AGENTS.md instead; D10).
- Cookiecutter or GitHub template repositories for vash init (not chosen: Copier proposed, as it also
  updates projects from the template; licences re-checked before adoption).
